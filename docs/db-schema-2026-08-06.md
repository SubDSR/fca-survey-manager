## Resumen y convenciones

- **38 tablas** en `public` (34 originales + `audit_log`, `carga_pendiente`, `revision_asignacion`), **13 vistas** (`v_*`) en `public` (11 originales + `v_seguimiento`, que ya no falta, + `v_asignaciones_sin_respaldo`, nueva), **10 tablas** en el esquema `staging`.
- **14 funciones** de aplicación (`fn_*`) y **19 triggers** (`tg_*`) — inventario completo por primera vez en este documento (no estaba en la versión 2026-08-04).
- RLS activo en **34 de las 38 tablas** de `public`. Ahora hay **4 excepciones**, no 1: `carga_csv` (la original, documentada a propósito) más `audit_log`, `carga_pendiente` y `revision_asignacion` (nuevas, sin RLS desde que se crearon — ver hallazgo 🔴 en la Parte 3).
- Los IDs son `smallint`, `bigint` según el volumen esperado de cada tabla (catálogos pequeños en `smallint`, tablas transaccionales en `bigint`).
- Varias tablas usan **claves foráneas compuestas** para forzar consistencia entre columnas relacionadas (ver `respuesta` más abajo).

- **7 vistas de reporte** ahora excluyen encuestas cuyo `curso_grupo_docente` tiene una incidencia `pendiente`/`descartada` en `revision_asignacion` (`v_encuesta_nota`, `v_encuesta_directivas`, `v_encuesta_seccion_efectiva`, `v_promedio_por_criterio`, `v_respuesta_detalle`, `v_docente_promedio_historico`, y transitivamente `v_docente_seccion_consolidada`/`v_seguimiento`) — **2 vistas se quedaron afuera de este cambio** por descuido: `v_docente_curso_consolidado` y `v_tasa_respuesta_pregunta` (ver hallazgo en Parte 3).

### v_seguimiento (ya no falta — bug 🔴 del documento anterior, resuelto)
Usada por `GET /encuestas/seguimiento`. Cruza `v_encuesta_nota` + `v_encuesta_directivas` contra la política de la campaña `ABIERTA`, y devuelve los docentes por debajo de `umbral_aprobacion` o con `%No` sobre el umbral, con `nivel_alerta` = `'CRITICO'` (peor que `umbral_critico_pct_no`, o nota bajo aprobación) | `'ADVERTENCIA'`.
```sql
WITH campania_abierta AS (
    SELECT ca.id AS campania_id, ca.politica_evaluacion_id
    FROM campania_evaluacion ca WHERE ca.estado = 'ABIERTA'
), politica_activa AS (
    SELECT pol.id, pol.umbral_aprobacion, pol.umbral_seguimiento_pct_no,
        pol.umbral_critico_pct_no, pol.min_encuestas_validas
    FROM politica_evaluacion pol
    JOIN campania_abierta cab ON cab.politica_evaluacion_id = pol.id
    LIMIT 1
), nota_docente AS (
    SELECT cgd.docente_id, avg(vn.nota_final) AS nota_promedio,
        count(DISTINCT vn.encuesta_id) AS n_encuestas_validas
    FROM v_encuesta_nota vn
    JOIN encuestado en ON en.id = vn.encuestado_id
    JOIN campania_abierta cab ON cab.campania_id = en.campania_id
    JOIN curso_grupo_docente cgd ON cgd.id = vn.curso_grupo_docente_id
    GROUP BY cgd.docente_id
), directivas_docente AS (
    SELECT vd.docente_id, sum(vd.n_no) AS n_no, sum(vd.total) AS total
    FROM v_encuesta_directivas vd
    JOIN encuesta e ON e.id = vd.encuesta_id
    JOIN encuestado en ON en.id = e.encuestado_id
    JOIN campania_abierta cab ON cab.campania_id = en.campania_id
    GROUP BY vd.docente_id
)
SELECT d.id AS docente_id, d.nombre_completo,
    round(nd.nota_promedio, 1) AS nota_promedio,
    round((100.0 * COALESCE(dd.n_no, 0)) / NULLIF(dd.total, 0), 0) AS pct_no,
    CASE
        WHEN nd.nota_promedio < pa.umbral_aprobacion
            OR (100.0 * COALESCE(dd.n_no, 0)) / NULLIF(dd.total, 0) >= pa.umbral_critico_pct_no
        THEN 'CRITICO' ELSE 'ADVERTENCIA'
    END AS nivel_alerta
FROM nota_docente nd
JOIN docente d ON d.id = nd.docente_id
LEFT JOIN directivas_docente dd ON dd.docente_id = nd.docente_id
CROSS JOIN politica_activa pa
WHERE nd.n_encuestas_validas >= pa.min_encuestas_validas
    AND (nd.nota_promedio < pa.umbral_aprobacion
         OR (100.0 * COALESCE(dd.n_no, 0)) / NULLIF(dd.total, 0) >= pa.umbral_seguimiento_pct_no);
```

### v_asignaciones_sin_respaldo (nueva)
Usada por `GET /api/revisiones` (`combinarConDetalle` en `revisiones.js`). Foto de la realidad actual: `curso_grupo_docente` con `es_carga_oficial IS NOT TRUE` que ya tiene encuestas. Deliberadamente no conoce `revision_asignacion` — el controlador combina ambas.
```sql
SELECT cgd.id AS curso_grupo_docente_id, cgd.docente_id, d.nombre_completo AS docente,
    a.id AS asignatura_id, a.nombre AS curso, pr.id AS programa_id, pr.nombre_corto AS programa,
    g.ciclo, g.seccion, count(e.id) AS n_encuestas, min(e.fecha_respuesta) AS encuesta_mas_antigua
FROM curso_grupo_docente cgd
JOIN docente d ON d.id = cgd.docente_id
JOIN curso_grupo cg ON cg.id = cgd.curso_grupo_id
JOIN asignatura a ON a.id = cg.asignatura_id
JOIN grupo g ON g.id = cg.grupo_id
JOIN programa pr ON pr.id = g.programa_id
JOIN encuesta e ON e.curso_grupo_docente_id = cgd.id
WHERE cgd.es_carga_oficial IS NOT TRUE
GROUP BY cgd.id, cgd.docente_id, d.nombre_completo, a.id, a.nombre, pr.id, pr.nombre_corto, g.ciclo, g.seccion;
```

## Parte 3 — Inconsistencias encontradas

Ordenadas por severidad. No se corrigió nada de esto (salvo el punto de datos residuales, ver nota) — queda para decidir prioridad.

### 🔴 Crítico — 3 tablas nuevas sin RLS, no documentadas como excepción
`audit_log`, `carga_pendiente`, `revision_asignacion` se crearon (migraciones `2026-08-04-audit-log.sql`, `2026-08-05-fuzzy-matching-carga-csv.sql`, `2026-08-04-revision-asignacion.sql`) sin ningún `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`, a diferencia de las 34 tablas restantes de `public`, que siguen todas el mismo patrón `p_lectura_autenticados`. Confirmado que el propio advisor de Supabase (via MCP `list_tables`) marca esto como hallazgo de seguridad **critical**: estas 3 tablas quedan completamente expuestas a los roles `anon`/`authenticated` (lectura y escritura sin restricción) para cualquiera con la clave pública del proyecto — a diferencia de `carga_csv`, cuya falta de RLS sí está documentada como decisión a propósito desde el 2026-08-04. Nadie decidió esto conscientemente para las 3 tablas nuevas; simplemente se copió el patrón de crear tabla + índices + trigger sin el paso de RLS.
**No se aplicó ningún fix** — la corrección (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY` + política `p_lectura_autenticados` igual al resto) es de una sola línea por tabla, pero cambia el comportamiento de acceso y debe decidirse, no aplicarse de oficio.

### 🟡 Vale la pena limpiar — `fn_eliminar_carga` no limpia `revision_asignacion`
`fn_eliminar_carga(p_carga_id)` borra `respuesta`→`encuesta`→`encuestado`→`carga_csv` en cascada, pero `revision_asignacion` no está `carga_id`-scoped (referencia `curso_grupo_docente_id`, dato de catálogo permanente) y la función no la toca. Si una carga que disparó `fn_detectar_revision_asignacion()` se elimina después, la incidencia `revision_asignacion` queda huérfana: sin ninguna encuesta que la respalde, invisible para `GET /api/revisiones?estado=pendiente` (que la filtra silenciosamente al combinarla con `v_asignaciones_sin_respaldo`, que ya no le encuentra fila) pero **presente para siempre** en la tabla, y resoluble solo si alguien conoce su `id` directo. **Confirmado empíricamente durante esta misma auditoría**: se encontró 1 fila así (`revision_asignacion.id=147`, creada 2026-08-06 01:01:09 UTC por una de las cargas de prueba de la tarea de optimización de `importarFilasCsv`, huérfana tras borrar esa carga) — era exactamente el desfase entre el conteo crudo de la tabla (36 `pendiente`) y lo que devolvía el endpoint (35). **Se limpió esa fila específica como parte de esta auditoría** (no es una decisión de diseño pendiente, era un residuo de prueba real). El gap estructural en `fn_eliminar_carga` que permitió que esto pasara sigue sin corregir.

### 🟡 Vale la pena limpiar — 2 vistas de reporte sin excluir `revision_asignacion` pendiente/descartada
`2026-08-04-excluir-revisiones-pendientes.sql` redefinió `v_encuesta_nota`, `v_encuesta_directivas`, `v_encuesta_seccion_efectiva`, `v_promedio_por_criterio`, `v_respuesta_detalle`, `v_docente_promedio_historico` para excluir encuestas con incidencia pendiente/descartada, y su comentario dice explícitamente que `v_docente_seccion_consolidada`/`v_seguimiento` heredan el filtro sin tocarlas. **`v_docente_curso_consolidado` y `v_tasa_respuesta_pregunta` no están en ninguna de las dos listas** — se quedaron con el filtro de `carga_csv.visible` (de la migración de 2026-08-02) pero sin el de `revision_asignacion`. Efecto concreto en `v_docente_curso_consolidado`: `n_encuestas` (que cuenta `encuesta` directo) incluiría una encuesta con incidencia pendiente, pero `nota_promedio` (que sale de `LEFT JOIN v_encuesta_nota`, que sí excluye) la mostraría `NULL` para esa misma fila — resultado inconsistente a medias. Impacto práctico hoy: **ninguno confirmado** — ningún controlador de `backend/src` consulta ninguna de las dos vistas (mismo hallazgo que ya señalaba el documento anterior sobre falta de consumidores).

### 🟡 Vale la pena limpiar — índice faltante en `revision_asignacion.curso_grupo_docente_destino_id`
`curso_grupo_docente_id` sí tiene índice (parcial, `ux_revision_asignacion_cgd_pendiente`). `curso_grupo_docente_destino_id` (la otra FK de la misma tabla, poblada al `reasignar`) no tiene ningún índice — un filtro o join por ese campo hace seq scan. Impacto hoy: mínimo (36 filas), pero es el único caso, de las 3 tablas nuevas revisadas, donde una FK se quedó sin el índice que sí tienen sistemáticamente las FK del resto del esquema (`ix_cgd_docente`, `ix_encuesta_cgd`, `ix_docente_contacto_docente`, etc.).

### 🟢 Cosmético — `fn_autoconsolidar_secciones` sin invocación automatizada
Existe, está documentada en comentarios de `importarEncuestas.js` como el mecanismo que "recogerá" las secciones dispersas en su próxima corrida, pero no hay ningún `.rpc('fn_autoconsolidar_secciones', ...)` en `backend/src`. Debe correrse manualmente (SQL Editor) o desde un proceso fuera del repo. Mismo patrón ya señalado en el documento anterior para el resto del pipeline de `staging`.

### 🟢 Cosmético — RLS de `staging` activado sin migración
Ver Parte 2. No es un problema de seguridad (el resultado es un candado total, más seguro que lo documentado antes), pero es un cambio de comportamiento sin rastro versionado.
